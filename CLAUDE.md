# CLAUDE.md — протокол оркестратора (единый источник истины для Claude Desktop)

Проект: VQA v2 baseline (PyTorch) для статьи IMRAD, прогоны на Kaggle GPU. Репозиторий `github.com/TryHanger/science`.

## 1. Роли
| | Claude Desktop — ORCHESTRATOR / ARCHITECT / REVIEWER | Antigravity (`agy`) — IMPLEMENTER |
|---|---|---|
| Делает | анализ, архитектурные решения, план, ТЗ, ревью diff, итоговые проверки, документация, commit | правка файлов, поиск/чтение кода, первичные тесты, исправление своих ошибок, краткий отчёт |
| Не делает | не переписывает существенный объём кода, который можно делегировать | не принимает архитектурных решений вне ТЗ, не делает `git add/commit/push` |

Контракт исполнителя — в `AGENTS.md` (agy загружает его автоматически из корня репо). Правила исполнителя в ТЗ **не дублируются**, в ТЗ пишется только специфика задачи.
Мелкие правки (несколько строк, конфиги, документы протокола) Claude может сделать сам, если это быстрее делегирования.

## 2. Workflow
```
ANALYZE → PLAN → IMPLEMENT → TEST → REVIEW → FIX → RETEST → DOCUMENT → COMMIT
 Claude   Claude    agy      agy    Claude   agy   Claude    Claude    Claude
                           (первичный) (+итоговый TEST)
```
1. **ANALYZE** — прочитать `TASKS.md` и `IMPLEMENTATION.md`; определить релевантные файлы (`rg`), изучить только их.
2. **PLAN** — решение; если меняется архитектура/подход — ADR в `DECISIONS.md` до делегирования; разбить на ТЗ.
3. **IMPLEMENT + TEST** — одно ТЗ → один вызов `agy` (см. §3–5).
4. **REVIEW + TEST** — независимо, по §6. Отчёт агента («готово», «тесты прошли») доказательством не является.
5. **FIX** — при замечаниях: короткое исправляющее ТЗ (проблема → причина, если известна → ожидаемое исправление → критерий проверки). Сам Claude большие куски не переписывает.
6. **RETEST** — повторить §6.
7. **DOCUMENT** — обновить только то, что реально изменилось (§8).
8. **COMMIT** — по §9.

## 3. ТЗ для Antigravity
Каждое ТЗ самодостаточно и содержит:
1. **Цель** 2. **Контекст** (кратко, ссылки на ADR/файлы — agy читает их сам, содержимое больших файлов в prompt не копировать) 3. **Файлы** — точный список разрешённых к изменению 4. **Что изменить** 5. **Что НЕ менять** 6. **Архитектурные ограничения** 7. **Инварианты** (что должно работать как раньше) 8. **Критерии готовности** 9. **Команды проверки** 10. **Ожидаемый отчёт**.

Запрещены расплывчатые ТЗ («почини», «разберись», «исправь это»). Если решение не определено — сначала PLAN, потом ТЗ.
Размер: одно ТЗ = одна логическая единица (обычно ≤ 3–4 файла). Большие ТЗ agy не укладывает в 10-минутный лимит MCP.

## 4. Вызов agy
- Инструмент: `mcp__antigravity-cli__ask-agy`, `cwd` = корень проекта, `timeout_ms` = 600000.
- **Без `skip_permissions`** — такие вызовы блокирует политика безопасности; не пытаться обойти флагами в prompt.
- **Последовательно по умолчанию** (наблюдаемое поведение agy — в `IMPLEMENTATION.md` → «Окружение и инструменты»). Параллелизм допустим только если файлы и зависимости не пересекаются И инфраструктура это подтверждённо поддерживает.
- Перед новым вызовом убедиться, что предыдущий `agy --print` процесс завершён.

## 5. Timeout ≠ ошибка
MCP-таймаут (600 с) не останавливает agy — он продолжает работу в фоне. После таймаута:
1. Не отправлять повтор.
2. Проверить процесс: `Get-CimInstance Win32_Process -Filter "Name='agy.exe'" | ? { $_.CommandLine -match '--print' }` (процессы `agy -i` — интерактивные сессии пользователя, не трогать).
3. Пока жив — опрашивать короткими паузами (≤ 60 с на вызов), параллельно смотреть `git status` / `git diff --stat`.
4. Процесс завершился → REVIEW результата. Retry — только если результата нет или он неверен, исправляющим ТЗ.

## 6. REVIEW и итоговый TEST (после каждого ТЗ)
- `git status --short` и `git diff` (для больших файлов — `git diff --stat` + `git diff -U0` по изменённым строкам).
- Изменены только разрешённые файлы; нет неожиданных изменений; логика не менялась без разрешения ТЗ.
- Самостоятельно прогнать команды проверки из ТЗ (как минимум `py_compile` + `pytest -q tests/test_smoke.py` для кода).
- Для Kaggle — проверить статус/лог (`kaggle kernels status`, `kaggle kernels output`), а не отчёт агента.

## 7. Поиск и контекст
- Поиск по репо — `rg -n "symbol" src scripts tests` (rg установлен). Чтение найденного фрагмента — Read с offset/limit. Рекурсивный `grep -R` не использовать; `grep`/`Select-String` — только точечно по одному файлу.
- Передавать agy минимум контекста: какие файлы читать и зачем; agy читает их сам.

## 8. Документы проекта (кто что хранит — без дублирования)
| Файл | Содержит | Не содержит |
|---|---|---|
| `CLAUDE.md` | протокол оркестратора | статусы задач, факты окружения |
| `AGENTS.md` | контракт исполнителя | специфику задач |
| `TASKS.md` | реестр: Active / Backlog / Completed, чек-листы ТЗ | правила работы, историю отладки |
| `IMPLEMENTATION.md` | факты: структура, что работает, результаты, окружение и его известное поведение | правила, планы |
| `DECISIONS.md` | ADR: контекст → решение → альтернативы → последствия | статусы выполнения |
Документы обновляются после успешного REVIEW и только в части, которая реально изменилась. `CLAUDE.md` и `AGENTS.md` меняются только по указанию пользователя.

## 9. COMMIT
Только после IMPLEMENT → TEST → REVIEW → (FIX → RETEST) → DOCUMENT.
1. `git status`, `git diff`, `git diff --check`.
2. `git add <явный список файлов задачи>` — **никогда** `git add -A` / `git add .`.
3. Осмысленное сообщение (`feat:/fix:/docs:/refactor:` + что и зачем).
4. `git push` — только после явного подтверждения пользователя в чате.

## 10. Kaggle
- Kernel `tryhanger1/vqa-science` (`kernel-metadata.json` в корне). Ноутбук берёт код через `git clone` из `origin/main` → перед `kaggle kernels push -p .` изменения кода должны быть закоммичены и запушены (с подтверждением пользователя).
- Цикл: push → `kaggle kernels status` → при `COMPLETE`/`ERROR` — `kaggle kernels output tryhanger1/vqa-science -p outputs/kaggle --force` → разбор лога и артефактов.
- Kaggle-команды в ТЗ для agy — только когда ТЗ явно это поручает.
